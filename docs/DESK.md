# RM 미팅 준비 (에이전트 부서, `desk/`)

RM 이 영업하러 가기 전의 앞단을 부서가 알아서 돈다: 공시·뉴스로 시장을 보고, 자금 조달이 필요해 보이는 회사를 선정하고, 그 회사를 분석해 미팅용 1pager 를 낸다.
RM 은 채팅으로 시키지 않는다. 아침에 미팅 추천 회사와 1pager 를 받는다. 회사를 지정해 1pager 만 받을 수도 있다.

사외 프로토타입이다. 공개 자료(OpenDART, ECOS, 뉴스 검색 API, 웹 검색)만 쓴다. 콜리포트, 수요예측 실명, 고객 커버리지 리스트 같은 내부 자료는 넣지 않는다.

## 1pager (RM 이 받는 것)

RM 이 훑어보고 **미팅을 잡을지**와 **무엇을 논의할지**를 정하는 한 장이다. 보고서도 제안서 초안도 아니다. 분량은 한 화면(25줄 안팎), 표 없음.

| 칸 | 내용 | 줄 수 | 누가 |
|---|---|---|---|
| 판단 한 줄 | 미팅 추천 · 모니터링 + 근거(사건 · 금액 · 시점) | 1 | 분석 담당(판단), 브리핑 담당(근거 문장) |
| 자금 수요 | 무엇 때문에, 얼마, 언제 / 조달 진행 현황 / 유동성 | 4 이내 | 브리핑 담당 |
| 당사 주관 이력 | 최근 발행 중 당사 대표주관 참여, 만기 도래분 중 당사 주관 회차, 주요 주관사 | 3 이내 | 코드(공시 자료에서 계산) |
| 미팅 아젠다 | 논의할 주제(명사형) + 참고 사례 한 줄 | 3 + 1 | 브리핑 담당 |
| 최근 동향 | 실적, 주요 공시·보도 | 3 이내 | 브리핑 담당 |
| 확인 필요 사항 | 공개 자료로 확인되지 않아 미팅에서 확인할 것 | 3 이내 | 브리핑 담당 |

- 분기 실적 · 차입 및 만기 · 조달 이력 · 동일 등급 발행 사례 표와 출처는 **근거 자료**(`brief.detail_md`)로 따로 두고 화면에서 접는다.
- 문체는 증권사 IB 내부 보고 문체(개조식 · 명사형). 작업 과정의 말(가설, 신호, 검증 상태 등)은 RM 이 보는 글과 화면에 쓰지 않는다. 지침의 `STYLE` 과 `render.JARGON` 이 지키고, 섞이면 검증 담당이 고친다.
- 미팅 판단은 셋이다: **미팅 추천**(자금 수요 확인 · 12개월 내 · 조달 방식·주관사 미정) / **모니터링**(수요는 있으나 시점이 멀거나 규모가 확인되지 않음) / **제외**(조달 완료 · 주관사 선정 · 자체 자금 충분 · 영업 제약). 제외는 1pager 없이 사유 한 줄만 남는다.

## 흐름

| 순서 | 팀 | 누가 | 하는 일 | 남기는 것 |
|---|---|---|---|---|
| 0 | 데이터팀 | 코드 (+ Haiku ×3 웹 검색) | 공시·금리는 기존 수집기(`ingest/`). 뉴스는 `desk/news.py`: 네이버 뉴스 검색 API 키가 있으면 그것으로, 없으면 뉴스 검색 담당이 검색어 묶음별로 웹 검색(구글 뉴스 RSS 는 자동 수집이 막혀 있어 쓰지 않는다). 검색어는 `ref.desk_news_queries` 행 | `raw.filings`, `raw.news` |
| 1 | 모니터링팀 | Haiku ×3 | 신규 공시(4묶음)와 기사에서 자금 조달로 이어질 수 있는 건을 선별. 상장폐지·횡령·해산은 '영업 주의'로 표시 | `desk.signals`, `desk.seen` |
| 2 | 소싱팀 | Sonnet | 회사별 선별 건(최근 14일)과 정기 점검 후보(공모채 만기 3~6개월 전, 메자닌 조기상환, 단기 차입 의존), 공급망 조회 결과(아래)에서 미팅 대상을 최대 3개사 선정, 자금 수요 요약 | `desk.leads` |
| 3 | 분석팀 | Sonnet ×3 + 웹 검색 | 자금 수요 · 상환 여력 · 조달 진행 현황 · 유의 사항을 확인하고 미팅 판단. 제외면 여기서 끝 | `leads.research` |
| 4 | 브리핑팀 | Sonnet ×3 | 1pager 의 글. 당사 주관 이력과 근거 자료는 코드가 공시 자료로 구성 | `leads.brief`, `brief_md` |
| 5 | 검증팀 | Sonnet ×3 + 웹 검색 | 작성 과정을 모른 채 1pager 를 공시 자료·재무제표·보도와 대조. 틀린 곳과 표현을 고치고, 근거가 서지 않으면 보류 | `leads.verify` |

- 선정한 회사를 먼저 적고 나서 분석한다. 검증을 거치지 않은 1pager 는 전달되지 않는다.
- 단계마다 결과를 붙여 둔다. 비용 상한이나 오류로 멈추면 다음 실행이 끝난 단계를 건너뛰고 이어 한다.
- 검토한 공시·기사는 다시 읽지 않고, 선정한 회사는 14일 동안 다시 선정하지 않는다.
- 에이전트 정의(지침, 출력 형식, 모델, 인원)는 `desk/agents.py` 한 곳에 있다. 호출마다 `desk.calls` 에 한 줄(일감, 요약, 토큰, 검색 수, 비용)이 남는다.
- DB 의 칸 이름과 상태값은 처음 만든 그대로다(`leads.hypothesis` = 자금 수요 요약, `questions` = 확인 사항, `kill` = 제외 사유, `status` 대기·게시·보류·기각 = 작성 중·전달·검증 보류·제외). 화면이 RM 의 말로 바꿔 보여 준다.

## 실행

```bash
python3 -m desk daily [--days 3] [--force]     # 하루 실행
python3 -m desk resume                         # 새 대상 없이, 끝내지 못한 대상만 이어서
python3 -m desk redo [--days 7]                # 최근 선정한 회사를 지금 기준으로 다시 분석 · 작성
python3 -m desk brief 롯데관광개발              # 회사를 지정해 1pager 만
python3 -m desk news                           # 뉴스 수집만
python3 -m desk fin 00231372                   # 재무 도구 결과 확인
python3 -m desk config                         # 사무실 화면 설정(JSON)
npm run test:desk                              # SQL 함수 시험 (PGlite)
npm run test:desk-run                          # 실행 코드 시험 (가짜 Supabase·Claude·OpenDART 로 전 구간)
```

GitHub Actions `desk-daily` 는 수동 실행만 둔다. 결과는 실행 요약과 첨부(`desk-out`), DB 의 `mart.v_desk_briefs`·`v_desk_board`·`v_desk_signals`·`v_desk_runs`·`v_desk_calls` 에 남는다.

## 화면

AX 플랫폼 Agent 갤러리의 'RM 미팅 준비' 카드에서 본다. 결과물 화면은 미팅 판단별 목록과 1pager(근거 자료는 접힘)를 보여 준다. 사무실 화면은 `mart.v_desk_runs`·`v_desk_calls` 를, 결과물 화면은 `v_desk_board`·`v_desk_briefs` 를 읽는다.
부서·에이전트 구성이 바뀌면 `python3 -m desk config` 결과를 AX 플랫폼의 `src/desk/config.json` 에 다시 넣는다.

## 공급망 (`desk/supply.py`)

공시 기반 공급망 지도(비공개 저장소 `supply-map` 의 DB)를 읽기 전용 계정으로 조회한다. 데이터를 이 저장소나 DB 로 복사하지 않는다. `SUPPLY_MAP_DB_URL` 이 없으면 이 단계는 건너뛴다.

| 조회 | 내용 | 쓰는 곳 |
|---|---|---|
| `viewer.orders` | 최근 90일 공급계약 공시 합계가 최근 연매출의 30% 이상인 상장사(건설 제외, 조건부 계약·정정 공시 제외), 최대 25개사 | 소싱팀 입력 '수주 급증 후보' |
| `viewer.suppliers` | 선별 건에 투자·증설이 있는 회사(최대 5개사)에 납품하는 상장사: 최근 2년 공급계약 상대방, 매출 10% 이상 주요 고객 | 소싱팀 입력 '투자·증설 회사의 협력사' |
| `viewer.position` | 선정한 회사의 주요 고객 · 최근 1년 수주 · 납품 상장사 | 분석팀 회사 자료, 근거 자료 '주요 고객 및 수주' |

- 수주나 전방 투자만으로는 선정하지 않는다(수주 합계가 연매출을 넘거나 다른 건과 겹칠 때). 증설·조달 계획은 공시로 확인된 것만 적는다.
- 계열사 간 거래(특수관계자)는 넣지 않는다. 회사는 양쪽 DB 가 같이 쓰는 DART 고유번호로 잇는다.
- 공급계약 수집이 14일 넘게 멈춰 있으면 실행 요약에 적는다(supply-map 의 수집은 그 저장소에서 따로 돈다).
- 조회 함수는 supply-map 의 `sql/012_desk_feed.sql` 이다.

## 켜는 순서

1. 이 변경을 병합한다.
2. 운영 DB 에 `supabase/migrations/20261122144336_desk.sql` 을 적용한다(2026-11-22 적용함).
3. 저장소 시크릿에 `ANTHROPIC_API_KEY` 를 넣는다. 뉴스를 쓰려면 네이버 뉴스 검색 API 키 한 쌍도 넣는다: `NAVER_HUB_CLIENT_ID`·`NAVER_HUB_CLIENT_SECRET`(네이버 클라우드 NAVER API HUB) 또는 `NAVER_CLIENT_ID`·`NAVER_CLIENT_SECRET`(네이버 개발자센터). 없으면 공시만으로 돈다.
4. 공급망을 쓰려면 supply-map DB 에 `sql/012_desk_feed.sql` 을 적용하고, 저장소 시크릿 `SUPPLY_MAP_DB_URL` 에 읽기 전용 계정(sm_viewer)의 세션 풀러 접속 주소를 넣는다. 없으면 공시·기사만으로 돈다.
5. `desk-daily` 를 수동으로 한 번 돌려 결과와 비용을 본다. 그 뒤 워크플로의 예약 주석을 푼다.

## 비용

실행 상한 `DESK_USD_CAP`(기본 5달러). 상한은 새 호출을 막는 방식이라 이미 시작한 호출만큼 넘을 수 있다. 기업 분석은 뒤 단계 몫 0.5달러를 남기고 시작한다.
첫 실행(2026-11-22, 공시 29건·대상 3곳, 3분 40초)은 1.63달러였다: 모니터링 0.002, 대상 선정 0.05, 기업 분석 건당 0.28~0.37(검색 5~7회), 1pager 작성 건당 0.04, 사실 검증 건당 0.26~0.28. 대상 한 곳을 끝까지 하면 약 0.6달러다.
모델은 환경변수로 바꾼다: `DESK_MODEL_MONITOR`, `DESK_MODEL_SCOUT`, `DESK_MODEL_RESEARCH`, `DESK_MODEL_BRIEF`, `DESK_MODEL_VERIFY`. 하루 대상 수는 `DESK_MAX_LEADS`.

## 확인되지 않은 것과 한계

- Claude API 와 OpenDART 재무 API 는 첫 실행(2026-11-22)에서 돌았다. 네이버 검색 API 는 키가 없어 아직 돌리지 않았다.
- 첫 실행에서 고친 것: 조사 담당이 '제외 조건 해당 없음'을 글로 적은 것을 해당으로 읽어 기각함(→ kill.hit 참·거짓으로), 검수 결과의 형식이 어긋나 결과를 잃음(→ 형식 보정, 호출 출력 기록), 검수가 글 칸에 표를 다시 그림, 유사 사례에 금융채·신종자본증권이 섞임(→ `desk_comps` 를 같은 종류로).
- 재무: 12월 결산 기준으로 보고서를 찾는다. 차입 합계는 계정 이름으로 더한 값이라 회사마다 겹치거나 빠질 수 있다. 4분기는 연간에서 3분기 누적을 뺀다.
- 뉴스: 검색어에 걸린 기사의 제목·요약 한 줄만 본다. 회사 이름이 DB 의 회사명과 정확히 같을 때만 회사 코드가 붙는다.
- 공급망: 공급계약 공시의 상대방이 법인으로 이어진 것은 약 40%다(익명·해외 상대방은 이름만 남는다). 건별 수주 공시가 없는 업종(식품·소재)과 사업보고서의 원재료 매입처는 아직 잡히지 않는다. 실제 DB 를 붙인 실행은 아직 하지 않았다(조회문은 운영 데이터로 확인, 흐름은 가짜 서버 시험).
- 주가·시가총액, 신용등급 변경, 사모사채 발행은 수집하지 않는다.
- RM 의 피드백(연락함·보류·제외)과 읽는 화면은 아직 없다.
